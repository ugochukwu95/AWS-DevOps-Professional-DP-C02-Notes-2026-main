# What is EC2 Image Builder?

EC2 Image Builder automates creating, testing, securing, distributing, and maintaining:
- Amazon Machine Images (**AMIs**)
- Linux and Windows images
- Container images published to Amazon ECR

It implements a repeatable **golden image** or **immutable infrastructure** process. Applications launch from a preconfigured, tested image instead of installing everything during boot.

## Why use Image Builder?
- Reduce manual AMI creation and configuration drift.
- Patch operating systems and rebuild images on a schedule.
- Apply reusable security-hardening and software components.
- Test images before distribution.
- Copy AMIs across Regions and share them across accounts.
- Publish container images to ECR.
- Retire old images with lifecycle policies.
- Integrate builds with EventBridge, SNS, CloudWatch, Inspector, and CI/CD.

Image Builder itself has no service charge. You pay for underlying resources such as temporary EC2 instances, EBS snapshots, S3 storage, ECR, data transfer, and scanning services.

## Core resources
| Resource | Purpose |
| --- | --- |
| Component | Reusable YAML document that installs, configures, validates, or tests |
| Image recipe | Parent AMI plus ordered build/test components and block-device mappings |
| Container recipe | Parent container image plus components and Docker settings |
| Infrastructure configuration | Build/test instance type, IAM profile, networking, logs, SNS, and termination behavior |
| Distribution configuration | Target Regions/accounts, AMI settings, launch permissions, or ECR destination |
| Image pipeline | Connects recipe, infrastructure, distribution, tests, schedule, and workflows |
| Workflow | Customizes build, test, and distribution stages |
| Lifecycle policy | Deprecates, disables, or deletes old images and related snapshots |

## Image pipeline flow
```text
Parent image
    +
Ordered build/test components
    ↓
Temporary build instance launched
    ↓
Components install software, patch, and harden
    ↓
AMI/container image created
    ↓
Temporary test instance validates image
    ↓
Image distributed to Regions/accounts/ECR
    ↓
Temporary resources cleaned up
```

If a build or test fails, the pipeline does not distribute the failed image.

## Recipes
An image recipe defines:
- Parent image
- Ordered build and test components
- Component parameters
- EBS block-device mappings
- Working directory and optional settings

The parent can be an existing AMI or an Image Builder image. A container recipe starts from a container base image and publishes the result to ECR.

Recipes and components are versioned resources. Create a new semantic version instead of modifying an existing version.

### Semantic versions
Image Builder resources commonly use:
```text
major.minor.patch
1.0.0
```

The complete resource ARN can also include a build version generated by Image Builder. Use version selection deliberately so a pipeline either stays reproducible or adopts approved dependency updates.

## Components
Components are reusable Amazon Web Services Task Orchestrator and Executor (**AWSTOE**) documents.

Common uses:
- Install packages or application binaries
- Apply Windows/Linux updates
- Configure OS settings
- Add certificates and monitoring/security agents
- Validate files, services, ports, and package versions
- Run application smoke tests

Use AWS-managed components where suitable or create organization-owned components for internal standards.

## Infrastructure configuration
Controls the temporary build and test environment:
- EC2 instance type(s)
- Instance profile and IAM role
- VPC subnet and security groups
- Key pair for exceptional troubleshooting
- S3 logging destination
- SNS notifications
- Terminate instance on failure
- Tags and resource settings

The build instance needs outbound access to Image Builder/Systems Manager endpoints and any package repositories or artifact locations used by components. Use NAT or VPC endpoints for private subnets.

## Distribution configuration
For AMIs, distribution can configure:
- Copies to multiple Regions
- AMI name and description
- Account, AWS Organizations, or OU launch permissions where supported
- KMS keys for encrypted copies
- License Manager configurations
- Fast launch settings for supported Windows AMIs

For containers, distribution publishes the final image to an ECR repository.

Cross-account AMI distribution requires destination-account permissions and compatible KMS key policies when snapshots are encrypted.

## Scheduling and triggers
Pipelines can run:
- Manually
- On a schedule using a rate or cron expression
- In response to automation/API calls
- When source dependencies change, according to pipeline schedule settings

Use EventBridge to react to Image Builder state changes and trigger notifications or downstream deployment workflows.

## Image lifecycle policies
Lifecycle policies keep image inventories manageable by applying actions based on age or count:
- **Deprecate**: Image remains usable but is marked as no longer preferred.
- **Disable**: Prevent normal use of the AMI.
- **Delete**: Remove the image and optionally associated snapshots.

Account for images referenced by launch templates, Auto Scaling groups, and rollback procedures before deletion.

## Image Builder vs related tools
| Requirement | Use |
| --- | --- |
| Managed AWS service for AMI/container build pipelines | EC2 Image Builder |
| Multi-cloud machine-image tooling | HashiCorp Packer |
| Select AMI, instance type, networking at launch | EC2 launch template |
| Small dynamic configuration at every boot | User data/cloud-init |
| Continuously enforce configuration on running nodes | Systems Manager State Manager |
| Patch running operating systems | Systems Manager Patch Manager |
| Deploy applications independently from base image | CodeDeploy, ECS/EKS deployment tooling |

**Exam tip**: Image Builder creates a new immutable image. Patch Manager changes existing managed nodes.
